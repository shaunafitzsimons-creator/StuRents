01 — Problem Framing

Problem Framing

What are we actually solving, and for whom?

The regulatory trigger

UK Government proposed legislation (2027) extends the sanctions checking obligation from a one-time check at contract signing to continuous monitoring throughout the tenancy. The obligation sits with letting agents — ABC's software fulfils it on their behalf.

The product problem

ABC's current system was designed for a single trigger: contract signing. It requires four new capabilities it does not have today:

Recurring check trigger Payment hold at mid-tenancy event External NCA integration Time-sensitive human review SLA

Who is affected

WhoHow
Letting agentsCompliance obligation sits with them — ABC must fulfil it. Failure exposes the agent.
TenantsCould have payments blocked and PII sent to NCA. Most will never know this system exists.
ABC OperationsManual review colleague faces material workload increase at volume.
ABC Commercial£120k/year new cost with no current revenue offset.
NCANew recipient of structured notifications — requirements not yet defined.

What success looks like

#Success condition
1Fully compliant before 2027 legislation comes into force
2No sanctioned tenant's rent payment is processed after a confirmed match
3NCA notified correctly and within a defined timeframe
4Letting agents have visibility of monitoring status without manual intervention
5Manual review workload is bounded by an SLA
6Cost of ongoing monitoring is priced into the product

03 — Edge Cases & Tensions

Edge Cases & Tensions

Where the current system has gaps, and where the new requirement creates complexity.

Timing tensions

The 9am–5pm window

Funds arrive at 9am, payout at 5pm. A match confirmed at 4:58pm must still block the 5pm payout. The system needs a real-time hold trigger, not a batch check. If human review is in progress at 5pm, the default must be: hold, not release.

12 exposure windows per year

Monthly rent = 12 moments per year where funds are in transit. The system must be ready to intercept at any of these, not just once.

Retrospective match after payout

If a match is confirmed after the 5pm payout, funds are with the letting agent — not ABC. The legislation says funds stay wherever they are "at the point the match is determined." Is ABC responsible for clawback? This is a legal question the product must handle both outcomes of.

Data quality issues

Self-reported vs. ID data

The automated check runs on tenant-typed data. A different transliteration or typo at onboarding returns a low score — never triggering human review. For ongoing monitoring: which data set do we run checks against?

Address data not currently collected

The NCA notification requires current address. We don't collect it today. This gap must be closed before R1 ships — either at onboarding or pulled from the tenancy agreement.

New obligations with no current equivalent

NCA notification

An outbound email to a government body containing PII is a new integration type. What is the required format? What is the timeframe? What happens if the email fails to send? Does ABC send directly or via the letting agent?

False positive mid-tenancy

A false positive at contract signing delays the tenancy starting. Mid-tenancy, it's worse: rent is frozen, tenant can't pay, agent is stuck. Resolving false positives quickly needs a defined and fast process.

Assumed workflow — manual reviewer (to be validated)

This is our current best guess at what this person's process looks like end-to-end. We need to sit with them and validate every step before drawing any conclusions or making any decisions.

🔔
1. Trigger received
~0 min
The automated check returns a confidence score ≥ 0.70. Something in the system notifies the reviewer that a case needs attention.
❓ How does the reviewer know? Email? Dashboard? A queue they have to manually check? We don't know.
🔍
2. Access the flagged case
~2–5 min
Reviewer navigates to the flagged check in the system, finds the associated tenancy, and locates the tenant's uploaded ID document.
❓ How many clicks to get there? Is the ID easy to find or buried? Is it always a readable file format?
🪪
3. Review the ID document
~5–20 min
Reviewer reads the name, date of birth, and nationality from the ID and cross-references against the flagged result. Assesses whether discrepancies between the self-reported data and the ID data explain the flag.
❓ ID quality varies widely — passport vs. driving licence vs. foreign ID. Transliteration differences, blurry uploads, or non-Latin scripts can add significant time here.
🔄
4. Re-run the check manually
~2–5 min
Using the data from the ID document (not the tenant's self-reported input), the reviewer re-runs the sanctions check manually. This is the definitive check — it corrects any discrepancies from the initial automated run.
❓ Does the reviewer use the same API tool the automated check uses? A different system? Manual OFSI list lookup? We don't know.
⚖️
5. Make a decision
~5–30 min
The reviewer determines whether the result is a match or no match and sets the status in the system. This is the highest-stakes step — an incorrect decision has direct legal consequences either way.
❌ No escalation path. If the reviewer is uncertain, there is currently no defined process for getting a second opinion or escalating. One person carries this alone.
📝
6. Document the decision
~2–5 min
The reviewer logs their decision and reasoning for the audit trail. Compliance decisions must be traceable — especially for any OFSI enquiry.
❓ Where does this get logged? In the system? A spreadsheet? An email? How formal is the trail? We don't know.

~15 min

~30 min
Common name, multiple possible matches on the sanctions list, requires careful comparison

~60 min

Does this person work evenings or weekends?

06 — Proposed Solution Flow

Proposed Solution Flow

End-to-end flow across three scenarios: no match, pending review, confirmed match mid-tenancy.

Key design decision: The payment hold is applied at the point of automated flag (score ≥ 0.70), not after human review confirms a match. Funds cannot move while a potential match is unresolved.

Scenario 1 — No match (expected for the vast majority)

Monthly schedule triggers ↓ Automated check runs for each active rent tenant ↓ Score < 0.70 → Status: 'no match' → logged with timestamp ↓ Rent payment cycle proceeds as normal 9am funds arrive → 5pm payout to letting agent

No human intervention. Audit log updated. Letting agent sees portfolio-level "all clear."

Scenario 2 — Automated flag, pending human review

Score ≥ 0.70 ↓ ⚠️ PAYMENT HOLD applied immediately Status: 'pending review' Letting agent notified: "Tenant under review, payment paused" ↓ Colleague reviews using ID document on file SLA: resolve before next 5pm payout ↓ No match confirmed Match confirmed ↓ ↓ Status: 'no match' Status: 'match' Hold released → Scenario 3 Funds paid at next payout Letting agent notified

Scenario 3 — Confirmed match mid-tenancy

Match confirmed by human reviewer ↓ Two simultaneous actions: PAYMENT HOLD — permanent NCA NOTIFICATION Funds remain in client Automated email sent: money account - Full name (from ID) All future payments blocked - Date of birth Letting agent notified - Current address Delivery logged + timestamped ↓ Audit log updated: match confirmed, NCA notified, payment blocked Case handed to compliance/legal for further action

What ABC does not do

Does not contact the tenant Does not determine what happens to the tenancy Does not clawback already-paid funds Does not replace legal counsel

08 — Ways of Working

Ways of Working

How I'd move this from problem to shipped at a 45-person company.

Principle: At a company this size, process should serve the work, not the other way around. Shared understanding, clear ownership, fast feedback loops, no surprises.

Discovery

Who: PM, one engineer, legal, manual review colleague

Start with the manual review colleague — they know where the current process breaks and what the real operational risk is. Most undervalued input on this problem.

Output: short problem brief (done), validated assumptions, open questions answered or escalated.

Spec and alignment

Who: PM, engineering lead, design (review queue + agent notifications), legal

Lean spec — not 20 pages. Covers: what the system must do, decision logic, scenarios, explicit out-of-scope. Flow diagrams are the primary communication tool.

One alignment session with engineering and legal together before build starts. Disagree early, not mid-sprint.

Build and review

Check in at start and end of each sprint — not daily. Prioritise unblocking over updating.

Test the critical paths personally before UAT: payment hold logic, 5pm payout behaviour, NCA email trigger. These are the scenarios where a bug has legal consequences.

Staged rollout: internal → pilot agents → full 100k. Never go straight to full scale on a compliance feature.

Stakeholder communication

WhoWhen
Engineering leadOngoing — as needed
Legal / complianceSpec stage + before release
Manual review colleagueDiscovery + UAT
Letting agentsBefore R1 ships — not after
Senior leadershipKick-off + before R1

What I would not do

No formal discovery sprint with workshops No 20-page PRD No gating progress on perfect legal clarity

The problem is well-defined and time-constrained. Lightweight alignment sessions are faster and sufficient. Build what we know, flag what's pending, don't let uncertainty become a blocker.
